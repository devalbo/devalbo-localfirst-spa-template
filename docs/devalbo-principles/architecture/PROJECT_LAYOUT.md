# Project layout

Where code goes, and which direction dependencies flow. This doc is the canonical home for
directory structure; other docs point here.

## The decision: layer-based

**Organize `src/` by layer — what a module _is_ — not by feature.**

One exception, imposed from outside: **`src/routes/` is path-shaped, not layer-shaped**,
because TanStack Router's file-based routing maps the file tree onto URLs. Keep route files
thin — a route composes components and owns nothing else.

A layer-based tree makes the **dependency direction** visible and enforceable: a schema can't
import a component, because schemas sit below components. That single property is what keeps
a codebase from turning into a graph where everything reaches everything, and it's worth more
here than feature locality.

The honest trade-off: a change to one feature touches several directories, and no single
folder shows you everything a feature contains. Feature-based slices win on that axis. They
lose on boundary enforcement — a `features/contacts/` folder has no inherent rule preventing
it from importing `features/billing/` internals, and in practice they do.

**When to revisit.** If this grows into many genuinely independent features with little shared
domain, feature slices become the better trade. That is a real fork, not a mistake — record
the decision if you take it ([SDLC_PROCESS.md](../practices/SDLC_PROCESS.md)).

## The tree

```
proto/                  .proto sources; buf module config
  <domain>/v1/*.proto

src/
  gen/                  generated from proto — committed, never hand-edited
  routeTree.gen.ts      generated by the router plugin — committed, never hand-edited
  wire/                 envelope logic + Zod refinements over generated types
  schemas/              Zod schemas for stored and local-only shapes
  store/                TinyBase setup; table, index, and value definitions
  commands/             the command layer
  hooks/                useSomething — stateful logic extracted from components
  components/           React components
  routes/               file-based routes; the file tree *is* the URL structure
  utils/                pure leaf helpers
  styles/               tokens.css + global.css — the design-system contract
  main.tsx              entry point

tests/
  setup.ts
  helpers/              store factory, render wrapper
  unit/                 mirrors src/

docs/devalbo-principles/  inherited doc set
```

## What each layer owns

| Layer         | Owns                                                            | Never contains                     |
| ------------- | --------------------------------------------------------------- | ---------------------------------- |
| `gen/`        | Generated protobuf types                                        | Anything hand-written              |
| `wire/`       | Envelope construction, signing, verification, decode + validate | React, direct store writes         |
| `schemas/`    | Zod schemas and derived types                                   | Business logic, store access       |
| `store/`      | Store creation, table/index/value names, persisters             | Domain rules                       |
| `commands/`   | Operations returning `CommandResult`                            | JSX, DOM, environment checks       |
| `hooks/`      | Stateful React logic, subscriptions                             | Markup                             |
| `components/` | Rendering and user interaction                                  | Business rules, direct persistence |
| `utils/`      | Pure functions with no project dependencies                     | Imports from any other layer       |

## Dependency direction

**Dependencies point down. Never sideways into a peer's internals, never up.**

```
        components/
             ↓
          hooks/
             ↓
        commands/
             ↓
    store/  ·  schemas/  ·  wire/
             ↓
          utils/          (leaf — imports nothing from src/)
```

Consequences worth stating plainly:

- **`utils/` imports nothing from `src/`.** The moment a util needs the store, it isn't a util
  — it's a command or a store helper.
- **`schemas/` and `wire/` import nothing above them.** They're the bottom of the domain, which
  is what makes them trivially testable.
- **`commands/` never imports React.** This is the rule that makes the command layer callable
  from tests, scripts, and agents ([COMMAND_LAYER.md](COMMAND_LAYER.md)).
- **`components/` never writes to the store directly** for anything non-trivial — it calls a
  command. Direct reads through hooks are fine.

**Enforce it, don't rely on discipline.** ESLint can fail the build on a violation
(`import/no-restricted-paths`, or `eslint-plugin-boundaries` for richer layer rules). An
architectural rule nobody checks is a preference. This is the same reasoning as gate-vs-report
in [TOOLING.md](TOOLING.md).

**Cycles are always a design error.** A cycle means two modules are really one, or a boundary
is in the wrong place. Split or merge; never break it with a lazy import.

## Growing a layer

When a layer gets large, **subdivide inside it by domain** — don't carve a feature slice
across layers:

```
src/components/contacts/ContactList.tsx     ✓ subdivided within the layer
src/features/contacts/ContactList.tsx       ✗ different architecture; pick one
```

Mixing the two is the worst outcome: you get neither enforceable direction nor feature
locality, and new code lands wherever the author looked first.

`components/` is usually the first to need this, and it's fine for one domain folder to hold
several small components plus their subcomponents.

## Colocation

Layer-based does not mean everything is spread thin. Colocate what only one thing uses:

- A subcomponent used by exactly one component lives beside it.
- A hook used by exactly one component lives beside it — promote to `hooks/` on the second
  consumer, not in anticipation of one.
- Styles live with their component as `<Component>.module.css`. Shared tokens live in
  `src/styles/tokens.css`; components consume token _names_, never raw values.

**Tests are the deliberate exception**: they mirror `src/` under `tests/unit/` rather than
sitting beside the source, so the test tree is separately navigable and the shared helpers
have an obvious home → [testing/unit-tests.md](../testing/unit-tests.md).

## Imports

**Use the `@/*` alias for cross-layer imports; relative paths within a folder.**

```ts
import { createContact } from "@/commands/contacts"; // crossing layers
import { ContactRow } from "./ContactRow"; // same folder
```

Alias imports decouple a module from its position in the tree, so moving a file doesn't
rewrite a dozen import lines. Relative imports inside a folder keep genuinely local
relationships visible. Setup: [SETUP_NEW.md](../operations/SETUP_NEW.md).

**Avoid barrel files** (`index.ts` re-exporting a folder). They obscure what actually depends
on what, defeat tree-shaking, and are a common source of import cycles — which is precisely
the property this layout exists to protect.

## Naming

- **Files match their default export**: `ContactList.tsx` exports `ContactList`.
- **Components** `PascalCase`; **everything else** `camelCase`; **directories** `kebab-case`
  or lowercase.
- **Hooks** start with `use`.
- **Tests** are `<subject>.test.ts(x)`, mirroring the source path.

File size limits and when to split are in [CODING_GUIDELINES.md](../practices/CODING_GUIDELINES.md).

## Generated and non-source files

- **`src/gen/` is committed and never hand-edited.** CI verifies regeneration produces no diff
  → [SERIALIZATION.md](SERIALIZATION.md).
- **`src/routeTree.gen.ts` is committed too**, for a different reason: `tsc` doesn't run Vite
  plugins, so a fresh clone must be able to typecheck before anything is built. Both are
  excluded from the linter and formatter — generated output is owned by its generator.
- **`proto/` sits at the repo root, not under `src/`** — it's a language-neutral contract, not
  TypeScript, and may later be shared with a non-TS consumer.
- **Non-rendered docs live outside the build** in `docs/`, never in a routed or bundled path.

## Browser-only code

Modules touching WebCrypto, WebRTC, or storage must not execute at import time — they'd break
prerender, SSR, or a test's module load. Keep those calls behind a mount effect or a
client-only boundary → [PROTOTYPE_BASELINE.md](../principles/PROTOTYPE_BASELINE.md).
